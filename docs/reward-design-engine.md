# 報酬設計・検証エンジン

## 実行API

`au_hikari_conditions.reward_design.design_agency_rewards` は、承認済みの上位単価・前月条件・直接原価を使い、目標粗利を満たす最小変更候補を返す。対象は基本報酬、キャンペーン、ISP、オプション。エンジンは候補を作るだけで、承認・帳票生成・送信は行わない。

- `AgencyRewardProfile`: 代理店ID、対象期間、目標粗利、最低粗利、単価変更可否、上位回収前に代理店へ支払うかを指定する。回収時期は契約根拠と承認証跡が必須。
- `RewardComponent`: 基本・ISP・オプション等の上位単価、前月代理店単価、直接原価、開通区分、支払可否、P2成果項目IDを指定する。上位・前月・原価の各証跡が承認済みでなければ保留する。FTTH開通手数料は`payment_component=FTTH_OPENING_FEE_COMPONENT`で識別し、承認済み上位単価が2,000円であることを確認した上で代理店支払を自動的に0円にする。
- `CampaignSchedule` / `CampaignTierInput`: 商流全体で判定する計数範囲、代理店向け報酬対象範囲、対象開通区分、適用方式、各閾値の単価・前月条件・原価を別々に渡す。
- `VolumeScenario`: 商流全体の達成件数と代理店側の対象開通件数を別々に指定し、単価×代理店対象件数の支払・粗利を検証する。
- `JudgmentReview`: 原本だけで自動確定できない契約・文言事項をAIレビュー／人手承認に分離する。未解決項目があると結果を保留する。

候補単価は前月単価を上限に、粗利制約を満たす最も近い金額とする。従って粗利に余裕があるという理由だけで代理店単価を増やさない。到達段階方式では、閾値が上がるほど単価が下がる候補を最小変更で修復する。累進方式は各段階の加算額として明示入力された場合のみ、到達済み加算額を合算して粗利を検証する。方式が不明な場合は提案を承認可能な状態にしない。

キャンペーンは各閾値の直前・到達時点、および対象開通区分ごとの単位案件をシミュレーションする。任意の`VolumeScenario`では実際の商流全体件数を閾値判定に使い、別に指定した代理店対象件数へ単価を適用する。計数件数は`counting_scope`、報酬適用件数は`payout_scope`として分離し、商流全体の件数を代理店の支払件数として扱わない。

## P2承認との接続

`connect_reward_design_to_p2` は、同一代理店・期間のP2結果が存在し、全対象成果項目が`proposed`で、上位単価・直接原価が一致することを検証する。いずれかの値がP2計算候補と異なる場合は`requires_p2_reapproval`を返す。`write_p2_reward_design_candidate` は元ブックを変更せず別名の候補ブックを作成し、提案単価から目標粗利を逆算してP2の粗利原価へ反映する。保存後読戻しとP2再計算を実行し、変更後の承認ハッシュ不一致で対象行が保留になることを確認する。承認状態・ハッシュは自動更新せず、正式なP2再承認後にのみ候補が通る。

未収時支払条件が不明、上位単価・前月条件・原価の承認証跡不足、最低粗利未達、単価逆転、未解決の人手判断がある場合は設計結果を`hold`にする。現行keiohのFTTH開通手数料は専用コンポーネントIDで識別し、上位受領2,000円、代理店支払0円として扱う。

## 既存データからの入力

P2の`粗利原価`、`条件対応`、`前回条件`、`承認管理`を入力の根拠に再利用する。既存v4ブックには、キャンペーン閾値ごとの階層単価や計数範囲、開通区分別の支払許可が構造化されていないため、エンジンAPIには承認済みの各行を明示して渡す。未承認候補を自動的に正式条件へ昇格する処理や、推測によるマスタ生成は行わない。
