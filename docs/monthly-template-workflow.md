# 月次の条件表作成・LOCK・PDF・下書き

現在の正規運用は、完成した共通Wordテンプレートへ代理店別の社名・金額・必要な個別条件を反映する方式。旧Phase 2の上位同等性131件を、毎月すべて承認し直す方式にはしない。条件表の承認、下書き作成の指示、送信の判断はそれぞれ別に扱う。

## 12月の流れ

1. `01_上位原本/2026-12/` に正しい12月上位原本を格納する。再送された修正版を正本とし、修正日等のファイル名差を条件変更として扱わない。参照したファイル名・SHA256は根拠として保持する。
2. 11月の確定済みWord2件を複製し、12月の共通テンプレートを作る。金額、対象期間、対象範囲、項目追加・終了、条項変更を反映する。通常条件とキャンペーン条件は別ファイルのまま、既存の書式・テキストボックス内の表も維持する。
3. 担当者が12月共通テンプレートを確認し、完成版を確定する。確認前のテンプレートから正式条件は作らない。保存例は `03_条件表/2026-12/` または `04_成果物/2026-12_テンプレート/`。
4. その完成版を各社へ展開する。正式社名、宛名、金額、ファイル名を置換する。継承、上位増減反映、個別設定の単価方針を代理店・成果項目ごとに反映する。基準は手動修正を含む11月LOCK版。新しい項目は12月の完成版を基準にする。
5. ネットコネクトの仮払い・入金確認等、個別条件は該当代理店だけへ反映する。販促支援金等の単価維持方針も引き継ぎ、変更指示がある場合だけ更新する。New Islandは明示的な再追加指示がない限り送付対象外。
6. 各社の条件表を確認・承認し、`04_成果物/2026-12_LOCK/` へバイト単位で同一のスナップショットを作る。Gitには金額本体を置かず、`docs/2026-12-conditions-lock.json` に指紋を固定する。11月LOCKを上書きしない。
7. LOCK済みWordを読み取り専用でPDF化する。各社の通常・キャンペーンPDF2件の対応と指紋を確認する。PDF化で条件文や金額を再計算しない。
8. `05_配信管理/` の当月マスタとメールテンプレートから、明示された対象だけをZoho APIで下書き保存する。宛先とPDFの対応、件名、宛名、添付数を検証する。送信は担当者がZoho画面で確認して手動実行する。

## 宛名と件名

- 宛名は `mail_company_name` と `mail_contact_name` を使う。担当者は必須、会社名は個人宛で空欄可。担当者欄の改行を維持し、旧 `mail_addressee` は使わない。
- 件名は `【{target_yyyymm}】【{subject_company_name}】auひかり(AL商流)/auひかりプラス_条件表通知表`。
- `target_yyyymm` は当月のYYYYMM、`subject_company_name` はマスタの正式名称に「様」を1回だけ付けたもの。個人宛も正式氏名＋「様」。
- 送信元はユーザーが指定したZoho登録済みアドレスを使う。主アドレスや他のアドレスへ自動的に切り替えない。

## 実装の使い分け

- `scripts/lock_conditions.py create/verify`：承認文書のスナップショット作成と改変検知。
- `scripts/export_locked_pdfs.ps1 -PlanPath <変換計画.json>`：Windows WordのPDF出力。変換計画は当月LOCKのマニフェストから作成する。月や社数は計画の内容で切り替わる。
- `scripts/run_locked_draft.py prepare --period 2026-12 --master <当月マスタ.xlsx> --template <メールテンプレート.json> --pdf-root <12月PDFフォルダ> --prepared <12月検証入力.json>`：当月のLOCK指紋・PDF・宛先・件名を照合する。12月実行前に12月LOCKと指紋の控えを用意する。
- `draft --agency-id <対象ID>`：明示された1社のみ保存する。作成指示と使用する入力の指紋が必要。
- `remaining-nine`：今回検証した10社編成で、keioh作成済みの後に残り9社を処理する補助操作。次月の対象や編成が変わる場合は、対象リストを先に更新・確認する。

フォルダへ12月原本を置くだけで、金額やテンプレートが自動確定する仕組みではない。共通テンプレート完成の確認と各社の最終承認は毎月必要。

## 下書きの安全な継続と表示名の扱い

同じ代理店・対象月の作成履歴があれば再作成しない。送信済みかどうかは担当者の操作結果であり、下書き作成履歴だけから推測しない。

添付名がZoho側で変わっても、承認PDF本体のSHA256と代理店・添付先が正しければ下書き保存まで進めてよい、というユーザー方針を採用する。元ファイル名とZoho返却名を保存し、`attachment_name_changed` と `requires_manual_review` で確認対象にする。LOCK原本やPDF本体を変更しない。

HTTP 415は生バイナリの転送型を `application/octet-stream` にして解消した。J&Cの半角 `&` はRAW・multipartの両アップロードで返却名から除去された。内部の除去理由は未確認。ユーザーが正しい名前の元PDFを手動添付して送信した実績を記録している。名前が変わったことは隠さず、下書き確認に回す。

保存APIの結果が不明な場合は自動再試行しない。添付アップロード段階で止まり下書き保存APIが未実行と確認できた場合だけ、明示的な再開操作を許可する。保存後のAPI再取得は別の確認事項であり、作成済み下書きをもう一度作る理由にはしない。自動送信機能は実装しない。
